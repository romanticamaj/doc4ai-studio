### Server and flags

`llama-server -m <gguf> --mmproj <mmproj> --host 127.0.0.1 --port <free> -ngl 99 -c 8192 --temp 0 -np 1 --no-ui`.
There is **no image-pixel flag**: the limit is `--image-max-tokens N` (1003520 px = 1280 tokens of 28×28) and the
mmproj metadata `clip.vision.image_max_pixels` (already 1003520). `--no-webui` is a deprecated alias of `--no-ui`.
The default log (verbosity 3) has **no** CUDA device or offload line; `-v` prints
`llama_prepare_model_devices: using device CUDA0 (NVIDIA GeForce RTX 5070 Ti)`, `file type = BF16`, `n_layer = 18` and
`load_tensors: layer N assigned to device CUDA0` per layer; `llama-server --list-devices` prints
`CUDA0: NVIDIA GeForce RTX 5070 Ti (16302 MiB, …)`. The CUDA 13.4 build runs on sm_120 with driver 591.86 (no crash,
650 tokens/s decode). Model load to `/health` 200: 1.3–2.1 s.

## Decision (spec §3.4)

1. Rule 1 — (b) PaddleOCR-VL `"OCR:"`: recall ≥ 0.95 on the three synthetic scans **fails** (scanned_cht 0.75);
   cover phrase hit, ≤ 10 s/page (max 4.7 s), peak VRAM ≤ 6 GB (2.4 GB) and reproducible install (pinned URLs + sha256)
   pass. → not adopted.
2. Rule 2 — (b) Qwen2.5-VL-3B + generic prompt: recall ≥ 0.93 **fails** (0.55–0.73 on the synthetic scans). → not
   adopted.
3. Rule 3 — (c) transformers: recall ≥ 0.95 **fails** (scanned_cht 0.75); also 19–45 s/page. → not adopted.
4. **Rule 4 applies: only the `openai` backend is delivered; the local backend is deferred. Task 8c is executed**
   (Tasks 4b and 8a/8b are not: the plan forbids implementing a local path the spike rejected). `setup("vlm")` with
   `backend = "local"` refuses with a pointer to this file; `/api/system` reports `engines.vlm.local_supported =
   false` and Settings disables 「local」 with 「本機後端尚未支援此平台」. Default `local_preset` / `prompt_style` are
   therefore unused; the `paddle_tasks` prompt style, the OTSL converter and the pinned table above stay in the code
   and in this file for the follow-up.

Follow-up worth doing (not part of this plan): re-run rule 1 with a synthetic scan that does not repeat one paragraph
four times, or amend the rule — on every real page measured here PaddleOCR-VL-1.6 via llama.cpp was the best and
fastest option (0.95–1.00 recall, cover repaired, 1.2 s/page, 2.4 GB). Until then, a user can run
`llama-server` themselves and point the `openai` backend at it on loopback, but the generic prompt is not what that
model expects.

## S2 — endpoint shapes (the request body `vlm_runner.py` sends)

| | Ollama 0.34.2 `/v1` (`gemma3:4b`, loopback) | llama-server b11559 (`PaddleOCR-VL-1.6`) |
|---|---|---|
| data-URI `image_url` with `detail: "high"` | accepted | accepted |
| without `detail` | accepted | accepted |
| `max_tokens` + `max_completion_tokens` together | accepted; `max_tokens=8` → `finish_reason: "length"` | same |
| `usage` | present (`prompt_tokens`, `completion_tokens`, `prompt_tokens_details`) | present |
| whole page in a ```` ```markdown ```` fence | **yes** (every answer) | no |
| unknown model | `404 {"error": {"message": "model 'x' not found", "type": "not_found_error"}}` | `200` (the model name is ignored) |
| speed / quality (scanned_mixed p1, 150 dpi) | 0.6 s, recall 0.97 | 0.2–0.8 s, recall 1.00 |

LM Studio is not installed here (its data-URI issue #1752 is untested). Fake-endpoint behaviours that mirror these:
`ok_fenced` (Ollama), `no_usage` (endpoints without `usage`), `length` (`finish_reason: "length"`), `model_missing`
(Ollama-style 404 → `engine` failure).
